# GitHub Profile Dashboard Design

## Goal

Turn `ljj13/ljj13` into a polished experimental GitHub Profile README for the display identity **FogPurification**, showing the requested profile widgets while avoiding broken placeholders and keeping the first screen clean.

## Identity and copy

- Never show the user's real name.
- Display name: `FogPurification`.
- Keep the repository/account identifier `ljj13` only where GitHub URLs or widget APIs require the current username.
- Header: GitHub avatar, display name, one-line Chinese slogan, animated typing line, Website/GitHub buttons, compact profile-view counter.
- Keep the visual language clean and engineering-oriented rather than cyberpunk or badge-heavy.

## Widget implementation strategy

### Repository-generated assets

Prefer GitHub Actions-generated SVG files committed to the profile repository wherever an Action supports the repository-scoped `GITHUB_TOKEN`.

- Existing snake remains generated into the `output` branch.
- Existing 3D calendar remains generated into `profile-3d-contrib/` on `main`.
- GitHub Stats + Top Languages use `Pranesh-2005/github-readme-stats-fast-action` to generate SVG assets under `profile-assets/`; this avoids the currently paused public `github-readme-stats.vercel.app` deployment.
- Profile Summary Cards should be generated by Action if the repository token is sufficient; if it is not, fall back to the hosted API only after checking that it returns a valid SVG.

### External widgets

Use only public endpoints that can be verified as returning a valid image during implementation.

- `readme-typing-svg`
- `skill-icons`
- Shields.io
- `github-readme-streak-stats`
- `github-readme-activity-graph`
- `github-profile-trophy`
- `github-profile-views-counter`

If an endpoint is down during verification, do not leave a broken image in the README. Prefer a repository-generated alternative if available; otherwise omit that one visual while keeping the section structure clean.

### Metrics constraint

`lowlighter/metrics` normally requires a user PAT for GitHub account-level data. The user explicitly does not want to be interrupted for setup. Therefore:

1. Try a public Metrics endpoint only if it is currently serving a valid image.
2. Do not request or fabricate a PAT.
3. If public rendering is unavailable, do not ship a broken Metrics image; retain the rest of the requested dashboard and document this constraint in the implementation notes.

## Visual rules

- Center the hero only; keep informational sections readable left-to-right.
- Use transparent/light-dark-friendly SVGs where supported.
- Use a restrained blue/gray visual language.
- Avoid stacking more than two dense cards side by side.
- Keep Trophy to a single row.
- Keep Metrics below Activity because it is visually dense.
- Preserve generous separators and whitespace.

## Automation

- Existing Snake and 3D workflows remain scheduled daily and manually dispatchable.
- Add a stats-assets workflow for local Stats/Top Languages generation.
- If Summary Cards Action works with repository token, include it in its own workflow; otherwise use hosted API URLs.
- Workflows that write assets need `permissions: contents: write`.
- New workflows should include `workflow_dispatch`, a daily `schedule`, and a narrow `push.paths` trigger for self-verification when their own workflow file changes.

## Verification requirements

Before completion:

- Confirm README contains no real name.
- Confirm all repository-local SVG paths exist.
- Confirm new workflows complete successfully.
- Confirm Snake and 3D assets still exist.
- Confirm every external image URL used in README is reachable as an image at verification time when tooling permits.
- Confirm no known-broken `github-readme-stats.vercel.app` URLs remain.
